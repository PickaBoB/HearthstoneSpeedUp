# Техническое описание

Как устроен HearthstoneSpeedUp внутри. Нативная часть не привязана к
Hearthstone: в консольном режиме (`GameSpeed.exe --pid ...`, см. ниже) она
работает с любым процессом и умеет два механизма. Окно использует только
Unity-механизм и только для Hearthstone.

Два механизма, потому что одного не хватает:

| Механизм | Что делает | Когда нужен |
| --- | --- | --- |
| **Unity timeScale** (`gsunity`) | ставит `UnityEngine.Time.timeScale` внутри рантайма игры | игры на Unity — там даёт ровные x30 |
| **Часы ОС** (`gsphook`) | подменяет таймеры Windows в процессе | любой другой движок |

По умолчанию выбор автоматический: инжектор смотрит модули целевого
процесса и берёт Unity-механизм, если находит там Mono или IL2CPP.

Проверено на мишенях x64 и x86: запрошенные x8, x16 и x30 дают ровно
x8.00, x16.00 и x30.00 по всем перехваченным часам, переключение на ходу
и возврат к x1 работают, процесс остаётся жив.

## Что он делает

Игра не хранит «скорость» отдельной величиной. Каждый кадр она спрашивает у
Windows, сколько прошло времени, и этим числом двигает всё: кадры анимаций,
интерполяцию, локальные таймеры, затухания. GameSpeed подменяет источники
времени внутри процесса игры на виртуальные часы, идущие в N раз быстрее
реальных. Игра получает «прошло 500 мс» вместо «прошло 16 мс» и проигрывает
эти 500 мс анимации за один кадр.

Перехватываются:

| Функция | Зачем |
| --- | --- |
| `QueryPerformanceCounter` | основной таймер почти всех движков, включая Unity и Unreal |
| `GetTickCount`, `GetTickCount64` | таймеры попроще, логика кулдаунов |
| `timeGetTime` (winmm) | старые движки и аудиосинхронизация |
| `Sleep`, `SleepEx` | иначе ограничитель кадров упрётся в реальный сон и съест весь выигрыш |
| `GetSystemTimeAsFileTime` | системные часы, **по умолчанию выключено** |
| `GetProcAddress` | чтобы поймать функции, которые игра находит в рантайме |

Виртуальные часы накапливают время, а не пересчитывают его от нуля: смена
множителя на ходу не даёт скачка назад, от которого движки ломаются. Дробный
остаток переносится между вызовами — без этого на x30 набегает дрейф.

## Чего он не делает

**Это не чит для онлайна и не обход анти-чита.** В DLL нет ничего, что бы её
скрывало: ни снятия чужих хуков, ни маскировки потоков, ни перетасовки
сигнатур. Патч таблицы импортов виден любому, кто посмотрит.

- В серверной игре состояние считает сервер. Локальные часы не ускорят добычу,
  откаты способностей или таймеры постройки — сервер считает их по своему
  времени. Ускорится ровно то, что рисует клиент: анимации, переходы, экраны
  ожидания.
- Рассинхрон с сервером даёт рывки, откаты позиции и дисконнекты.
- Любой анти-чит (EAC, BattlEye, VAC, Vanguard) видит и инжект, и патченый
  импорт. Это бан аккаунта, и утилита ничего с этим не делает.

Применение, под которое это писалось: одиночные и оффлайн-игры, пропуск
локальных анимаций, отладка своих сборок.

## Сборка

```
powershell -ExecutionPolicy Bypass -File build.ps1
```

Нужны:

- **.NET 8 SDK** — для инжектора.
- **Компилятор C** — для `gsphook*.dll` и мишени. Скрипт берёт первый
  найденный: `zig cc`, `cl.exe` (MSVC), `gcc` (MinGW). Zig ищется и в папке,
  куда его кладёт winget, так что перезапускать оболочку после установки не
  нужно.

Если компилятора нет:

```
winget install -e --id zig.zig
```

Zig весит около 80 МБ, не требует Windows SDK и собирает сразу обе
разрядности. Альтернатива — VS 2022 Build Tools с рабочей нагрузкой
«Разработка на C++» (несколько ГБ).

Только GUI: `build.ps1 -SkipNative`. Только нативную часть:
`build.ps1 -SkipInjector`.

Вручную:

```
zig cc -target x86_64-windows-gnu -shared -O2 -s -o bin/gsphook64.dll src/hook/gsphook.c -lkernel32 -luser32
zig cc -target x86-windows-gnu    -shared -O2 -s -o bin/gsphook32.dll src/hook/gsphook.c -lkernel32 -luser32
```

## Как пользоваться

Окно заточено под Hearthstone:

1. Запустить `bin\GameSpeed.exe` — до игры или после, неважно.
2. Окно само найдёт процесс `Hearthstone`, дождётся загрузки Mono и внедрит
   Unity-модуль. Если игра перезапустится, окно подключится к новому
   процессу.
3. Выбрать **x1 / x2 / x3 / x8**. Из игры то же делают **Ctrl+Alt+1..4**.

Ускоряются только бой и розыгрыш (см. раздел «Hearthstone» ниже), в простое
скорость x1. Строка «Сейчас» показывает текущий `timeScale` и фазу.

Для других игр и хука часов ОС остаётся консольный режим.

Снять хук на ходу нельзя — перезапустите игру.

Если игра запущена от администратора, запускайте GameSpeed тоже от
администратора, иначе `OpenProcess` вернёт отказ в доступе.

### 32-битные игры

`GameSpeed32.exe` — обычное .NET-приложение и требует **32-битный**
.NET 8 Desktop Runtime, отдельный от 64-битного:

```
winget install -e --id Microsoft.DotNet.DesktopRuntime.8 --architecture x86
```

Без него apphost показывает модальное окно «установите .NET» и ждёт нажатия
— запущенный из скрипта, он просто повиснет. Сама `gsphook32.dll` от .NET не
зависит.

Внедряться можно только в процесс своей разрядности: `LoadLibraryW` вызывается
удалённым потоком по адресу, взятому из собственного kernel32, а у 32- и
64-битных процессов он разный. Поэтому две сборки, а не одна универсальная.

### Консольный режим

То же самое без окна, для скриптов:

```
GameSpeed.exe --pid 1234 --inject --speed 8 --hold 10
GameSpeed.exe --pid 1234 --speed 30
GameSpeed.exe --pid 1234 --inject --method unity --speed 30
```

`--method` принимает `auto` (по умолчанию), `unity` или `clock`.
`--force` внедряет даже в процесс, уже стоящий под хуком, — чтобы догрузить
пересобранный `gsunity` без перезапуска игры (для `clock` не нужно).

`--hold <сек>` печатает фактическое ускорение. Управление можно передать
другому экземпляру: блок общей памяти переживает выход контроллера, потому
что DLL держит на него свою ссылку, и новый экземпляр его подхватывает.

## Проверка

`bin\testclock.exe` — мишень вместо игры. Читает те же часы и печатает, во
сколько раз каждые спешат относительно реального времени:

```
  real s        QPC   GetTickCount64   timeGetTime
     3.0   x    1.00   x        1.00   x     1.00
     5.0   x    4.61   x        4.60   x     4.61     <- хук включён посередине секунды
     6.0   x    8.00   x        8.00   x     8.00
    12.1   x   16.00   x       16.00   x    16.00
    18.2   x   30.00   x       30.00   x    30.00
    24.3   x    1.00   x        1.00   x     1.00
```

`testclock32.exe` — то же самое для ветки x86, проверять её нужно
`GameSpeed32.exe`.

Мишень намеренно написана на C, а не на .NET: C-программа берёт функции
времени через таблицу импорта — ровно то, что патчит хук, — тогда как .NET
резолвит `DllImport` лениво и кэширует сырой указатель, так что пришедший
позже инжект до него уже не достаёт. Это же и есть граница применимости: до
кода, который зовёт таймер мимо таблицы импорта, хук не дотянется. Движки
игр нативные, у них импорты на месте.

Флаг `--wall` при проверке не ставьте: мишень считает реальное время по
системным часам и с ним покажет x1.

## Почему для Unity нужен отдельный механизм

На движке Unity подмена часов ОС упирается в потолок, и это не дефект
инжектора, а устройство движка.

Unity ограничивает `Time.deltaTime` значением `Time.maximumDeltaTime`, по
умолчанию **1/3 секунды**. Хук отдаёт движку огромный кадровый интервал, а
движок его обрезает: при реальных 60 к/с и запрошенном x30 кадр «весит»
500 мс, но `Time.deltaTime` вернёт 0.333; при 30 к/с запрос — целая секунда,
а вернётся всё те же 0.333. Значит всё, что движок считает по
масштабируемому времени — аниматоры, корутины с `WaitForSeconds`, твины по
`Time.time` — не разгонится выше примерно x10–x20, и потолок тем ниже, чем
меньше реальный FPS.

Хуже того, `Time.unscaledDeltaTime` обрезку игнорирует. Код на нём ускоряется
полностью, аниматоры — нет, и вместо чистого ускорения получается рваная
картинка с разъезжающимися по скорости частями интерфейса.

Правильный рычаг для Unity — `Time.timeScale`: он множит время внутри
движка, уже после обрезки, поэтому x30 остаётся x30 и всё масштабируемое
едет согласованно. Это и делает `gsunity.dll`, вызывая рантайм игры через
его собственный встраиваемый API:

```
Mono    mono-2.0-bdwgc.dll / mono.dll / …   mono_*
IL2CPP  GameAssembly.dll                    il2cpp_*
```

Обе ветки устроены одинаково — найти домен, прицепить к нему поток, достать
класс `UnityEngine.Time` по имени, вызвать `set_timeScale`, — поэтому их
обслуживает один код с разными префиксами символов. Заодно модуль множит
`Time.fixedDeltaTime` на тот же коэффициент: шаг физики фиксированный, и без
этого при timeScale 30 движок выполнял бы тридцатикратное число
`FixedUpdate` за кадр и захлебнулся бы.

Многие игры сами пишут в `timeScale` (паузы, замедления, смена фаз — в
Hearthstone, например, после боя), поэтому модуль каждые 200 мс сверяет
значение и возвращает своё. Исходный `fixedDeltaTime` хранится в общей
памяти: модуль, догруженный поверх работающего (`--inject --force`), иначе
принял бы уже умноженный шаг за исходный. Новый экземпляр забирает управление,
старые останавливаются.

### Hearthstone

Hearthstone сам управляет временем через `Blizzard.T5.Core.Time.TimeScaleMgr`:
`Time.timeScale = m_gameTimeScale * m_timeScaleMultiplier`. Бой Полей
сражений плавно разгоняет первый множитель, таверна сбрасывает его в 1. Если
`gsunity` находит этот класс, он ставит свой коэффициент через
`SetTimeScaleMultiplier`, то есть умножает скорость игры, а не перебивает её.

Окно всегда работает в избирательном режиме (в консоли — `--selective`):
коэффициент действует только пока клиент проигрывает действия с сервера —
розыгрыш карты, атаку, каждый шаг боя — и всю фазу боя Полей сражений.
В остальное время скорость x1, так что таблица соперников, существа в таверне
и наведение на карты идут как обычно. Сигналы — чтение полей, игровой код из
чужого потока не вызывается:

```
GameState.s_instance.m_powerProcessor.m_currentTaskList != null   действие идёт
GameState.s_instance.m_gameEntity (TB_BaconShop).m_gamePhase == 2  фаза боя
```

После действия ускорение держится ещё 0.6 с, чтобы не мигать между
соседними пачками действий. Анимация, которая идёт одновременно с
действием, ускоряется вместе с ним: время в Unity одно на всех.

Если механизм выбран неверно, поле «Фактически» это покажет: запрошено x30,
фактически около x10 — значит работают часы ОС там, где нужен timeScale.

Отдельный потолок — у сетевых игр: клиент проигрывает присланную сервером
последовательность и между шагами ждёт ответа. Часы не заставят пакеты
приходить быстрее.

## Диагностика

Каждый модуль пишет свой лог рядом с временной папкой:

- `%TEMP%\gsphook_<pid>.log` — этапы запуска, сколько импортов пропатчено в
  каждом модуле, какие пропущены, смены множителя, необработанные исключения
  с кодом и адресом.
- `%TEMP%\gsunity_<pid>.log` — какой рантайм найден, какие экспорты
  разрешились, в какой сборке нашёлся `UnityEngine.Time`, исходный
  `fixedDeltaTime`, каждая установка timeScale и брошенные рантаймом
  исключения.

Собрать без логирования: `-DGSP_NO_LOG`.

В игру внедряется не `bin\*.dll`, а её копия
`%TEMP%\GameSpeed\<имя>_<хэш содержимого>.dll`. `LoadLibraryW` по уже
загруженному пути молча возвращает старый модуль, так что пересобранная DLL,
внедрённая под прежним именем в игру со старой сборкой, просто не
запустилась бы. Заодно `bin\` не блокируется запущенной игрой.

Если `gsunity` не нашёл рантайм за 60 секунд, он сдаётся и сообщает об этом
в окно («Рантайм Unity не найден») отдельным состоянием, чтобы это не
путалось с «ещё не ответил». Выдержка нужна потому, что внедряться в игру
на старте нормально, а Mono или `GameAssembly.dll` подгружаются не сразу.

## Устройство

```
src/hook/gsphook.c        часы ОС: виртуальные часы + патч таблиц импорта
src/hook/gsunity.c        Unity: Time.timeScale через Mono/IL2CPP
src/injector/             GUI-инжектор на WinForms
  Native.cs               P/Invoke
  SharedCtl.cs            блок общей памяти, 40 байт
  Injector.cs             LoadLibraryW в удалённом потоке
  Cli.cs                  консольный режим
  MainForm.cs             окно
src/testtarget/testclock.c нативная мишень для проверки
build.ps1                 сборка всего в bin/
```

GUI и DLL общаются через именованную общую память
`Local\GameSpeedCtl_<pid>`. Блок создаёт GUI **до** инжекта — так права на
него остаются за GUI, а DLL его только открывает. DACL блока открыт для
`Everyone`: иначе игра и GUI, запущенные с разным уровнем прав, не увидели бы
друг друга. Платой идёт то, что любой локальный процесс может сменить
скорость уже захваченной игры; внутри блока лежит только множитель.

Хуки ставятся патчем IAT, а не перезаписью пролога: не нужен дизассемблер
длин инструкций и нет шанса испортить горячий код.

### Две ловушки, на которые это уже наступило

**Рекурсия через переходники kernel32.** Экспорт `kernel32!Sleep` (и
`QueryPerformanceCounter`, и `GetTickCount64`) на актуальной Windows — не
реализация, а переходник вида `jmp [__imp_Sleep]`, уходящий через
*собственную* таблицу импорта kernel32 в kernelbase. `GetProcAddress`
возвращает адрес этого переходника. Если пропатчить и IAT самого kernel32,
то `real_Sleep` прыгает обратно в хук — бесконечная рекурсия, и через
несколько миллисекунд после инжекта процесс падает с `c00000fd`
(переполнение стека). Поэтому `ntdll`, `kernel32`, `kernelbase`, `win32u` и
заглушки `api-ms-*` / `ext-ms-*` не патчатся никогда, плюс отдельно
пропускается модуль, внутри которого физически лежит перехватываемая
реализация — проверкой диапазона адресов, а не по имени.

**Счётчик обновлений.** DLL раз в 250 мс перечитывает множитель и сверяет
`seq`. Контроллер, запущенный заново, начинает нумерацию с нуля и повторяет
номера, которые DLL уже видела, — смена скорости тогда молча игнорируется.
Поэтому новый контроллер подхватывает `seq` из существующего блока, а DLL
дополнительно сверяет само значение множителя. Значение в блоке всегда уже
ограничено диапазоном, который применяет DLL, иначе сверка не сошлась бы.

Рабочий поток DLL раз в 250 мс заново проходит по модулям: рендерер, mono и
плагины подгружаются позже основного образа.
